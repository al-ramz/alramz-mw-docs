**Error-code registry reuse (per skill step 4)**: before building either HTTP Status Code Reference table, searched the project's `Error-Code-to-HTTP-Status-Mapping.md` and found the one legacy code present in this package (`1012` — No Data Available) already registered there, mapped to HTTP 404. No new HTTP-status mappings were invented. Both services otherwise only ever set literal `"200"`/`"500"` — no separate legacy scheme beyond `1012`, verified directly against both flow.xml files (documented explicitly in Sections 4.6/5.6, matching the DFM/SocialMedia docs' "source-verification note" convention).

**Prefix scheme** — proposed, not yet user-confirmed: `RMG` (getRelationshipManagers), `CBR` (getCommissionsByRelationshipManager). No collisions with any existing scheme in this project (DFM: ONB/AUP/CFE/CIS/CLD/CON; SocialMedia: FBT/FBU/LIT/LIU/GMU/APU).

**Significant findings surfaced (consolidated in Appendix D of the doc, not fixed in source)**:
- **High severity**: (1) The commissions adapter's dynamic SQL substitutes `condition`, `startDate`, and `endDate` via webMethods' `${var}` textual-substitution syntax rather than `:var` bind parameters, with no format validation upstream anywhere in the calling Flow — a SQL-injection-shaped construction pattern, source-verified (the adapter declares zero bound input fields). (2) The Islamic-office clause (RM code `3031`, `SC_ISLAMIC='Y'`) and the general `CL_RELATION_MANG IN (...)` clause are AND-ed rather than OR-ed in the condition-builder — requesting `3031` together with any other RM code produces a self-contradictory `WHERE` clause and silently returns `404`/No Data instead of the union of both RMs' commissions. The adapter's own SQL retains a commented-out original condition using `OR`, directly confirming this is a regression rather than the intended design.
- **Medium severity**: The live commissions adapter (`AlgoIntegrations.adapters:getCommissionsByRelationshipManager`) is not in this export — the package bundles an unused, identically-shaped local copy of the same name under `AlRamzPortal.adapters`, which the SQL in Section 6.2 is reconstructed from (flagged throughout as high-confidence inference, not directly verified source). A declared `lastError` output field (`pub.event:exceptionInfo`) is never cleared on success and is repopulated unconditionally after every call — possible internal-exception leak on `500` responses. `CB_RELATION_MANAGER`'s `RM_DISABLES` flag is never filtered by `getRelationshipManagers`' query.
- **Low severity** (3 items): commission/volume totals summed via a string round-trip (`objectToString` → `addFloats` → `toNumber`) rather than native decimal arithmetic; neither response envelope includes a `correlationID` unlike the org standard used elsewhere in this programme; `startDate`/`endDate` defaults only apply when the field is entirely absent, so an empty string bypasses the default and surfaces as an untargeted `500`. One further **contextual** (non-severity-ranked) observation: the commissions service's success-path pipeline cleanup deletes several fields (`getMarketMakingTradesOutput`/`Input`, `userCode`, `type`, `RM1`–`RM3`, `RM`) that never otherwise appear in this Flow — evidence it was cloned from an `AlgoIntegrations` "market-making trades"–style service and not fully cleaned up; useful context for locating the real adapter dependency, no functional effect observed.

**Verification performed**: LibreOffice headless → PDF → `pdftotext -layout`, 22 content pages + 1 trailing blank form-feed page (expected). One real bug caught and fixed during verification: the helper module's table-cell/callout text rendering was spreading already-constructed `TextRun` instances (`{...r}`) instead of passing constructor options, which silently rendered every `DataTable` body cell and `CalloutNote` line as empty text — headers/borders looked fine, but no data appeared. Fixed by having `parseInline()` accept size/bold options directly and having `cellPara`/`CalloutNote` consume its returned `TextRun` array as-is rather than re-wrapping it. Re-verified visually (rendered representative pages to PNG and read them) after the fix — all tables and callouts now render correctly.
